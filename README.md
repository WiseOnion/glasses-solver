# Glasses Solver

A small iPhone app. Tap **Solve**, and it takes a photo with your Ray-Ban Meta glasses and sends it to Claude (`claude-opus-5-5`) with the prompt *"Solve the problem in this photo step by step. Keep it short and plain enough to hear read aloud."* It then speaks the answer through the glasses.

You can also tap **Start Session** for hands-free use: the session stays open in the background, and each press of the **capture button** on the glasses frame does the same thing as Solve, with a prompt you can edit for that session.

- Glasses access: [Meta Wearables Device Access Toolkit](https://github.com/facebook/meta-wearables-dat-ios) **1.0.0** (`MWDATCore`, `MWDATCamera`, `MWDATInputs`) via Swift Package Manager.
- Project file: generated by [XcodeGen](https://github.com/yonaskolb/XcodeGen) from `project.yml`. No `.pbxproj` is committed.
- Build: GitHub Actions (`macos-26`, Xcode 26.6) builds an **unsigned** `.ipa`. You sign and install it with Sideloadly.

## Secrets

- **Anthropic API key:** you type it into the app (Settings). It is stored in the iOS Keychain and is never in the repo or the build.
- **Meta App ID / Client Token:** optional. If you add the repo secrets `META_APP_ID` and `META_CLIENT_TOKEN`, CI writes them into `Config/Secrets.xcconfig` at build time. Leave them unset to use Developer Mode, which is what you want for personal sideloading.
  - Note: the values end up inside the built `.ipa`'s Info.plist. On a public repo, any signed-in GitHub user can download workflow artifacts. That is why retention is set to 3 days. Meta's client token is designed to ship inside apps, but if you'd rather not publish it at all, leave the secrets unset.

## Entitlements

There is no entitlements file. Everything here works with a free Apple ID:
- Meta registration and permission callbacks use a **custom URL scheme** (`glassessolver://`). **No Associated Domains / universal links** are needed.
- The Keychain uses the app's default access group, so no keychain entitlement is needed.
- Meta's CameraAccess sample also declares the Hotspot Configuration and Access Wi-Fi Information entitlements. The SDK docs only require Info.plist keys for the Wi-Fi link, so they're left out here.

## 1. Meta setup

**Developer Mode (needed, free):**
1. On your iPhone, update the **Meta AI** app and make sure your glasses are paired and up to date.
2. In Meta AI, go to **Settings → App Info** and tap **App version** five times.
3. Turn on **Developer Mode** and tap **Enable**. (The SDK repo describes it as Settings → Your glasses → Developer Mode. Menus vary by app version.)
4. After you first connect from Glasses Solver, it shows up under **Settings → App connections → Developer mode apps**.

**Wearables Developer Center project (optional, only for publishing/release channels):**
1. Sign in at https://wearables.developer.meta.com/ and click **New project**. Give it a name and description.
2. Under **Configuration**, add an iOS app with bundle ID `com.glassessolver.k7q3m2` (no hyphens allowed). This must match `Config/Base.xcconfig`.
3. Under **Permissions**, request **Camera** and give a short justification.
4. Copy the App ID and Client Token into the GitHub repo secrets `META_APP_ID` and `META_CLIENT_TOKEN`.
5. Caveat: non-Developer-Mode registration also checks your Apple **Team ID**. Sideloadly re-signs with your free "Personal Team", which isn't set at build time, so stay in Developer Mode for this setup.

## 2. Get the .ipa

1. Push to `main` (or open **Actions → Build unsigned IPA → Run workflow**).
2. When the run is green, open it and download the **GlassesSolver-unsigned-ipa** artifact.
3. Unzip the download to get `GlassesSolver-unsigned.ipa`.

4. In Sideloadly, drag in the `.ipa`, enter your Apple ID, and click **Start**. Enter the 2FA code if asked.

## 4. Test

1. Open **Glasses Solver → Settings**, paste your Anthropic API key (`sk-ant-…`), and tap **Save key**.
2. Tap **Connect glasses**. Meta AI opens; approve the app; you return to Glasses Solver. Status should read *Meta AI: registered*.
3. Put the glasses on with the hinges open. Status should read *Glasses: connected*. They should also be connected as Bluetooth audio, which is how the spoken answer reaches their speakers.
4. Look at a printed problem (e.g. `3x + 7 = 22`) and tap **Solve**. The first time, the app asks to open Meta AI for **camera permission**; choose *Allow always*.
5. You'll hear "Got it. Working on it.", then the answer. The photo and answer text also appear on the phone, with **Repeat** and **Stop** buttons.
6. If the text in your photos is too blurry, turn on **Settings → High-resolution photo (experimental)**.

**Test mode (free, no Claude)**
Turn on **Settings → Test mode (no Claude)** to test everything except Claude without an API key or credits. Presses and the Solve button run the real flow (glasses session, capture button, photo, speech), but instead of calling Claude the app waits and then speaks a sample answer that includes the photo's size. With the phone locked the wait is 35 seconds, longer than iOS's usual background allowance, so hearing "the app stayed running with the phone locked" confirms that locked-phone use works. An orange "Test mode" line on the main screen shows it's on.

**Hands-free session (capture button)**
1. Tap **Start Session**, edit the prompt if you like, and tap **Start**. You'll hear "Session started." A green **Session** badge and a session card appear in the app.
2. Look at a problem and press the **capture button** on the glasses frame (short press). It runs the same flow as Solve with the session's prompt.
3. You can leave the app or lock the phone. On the glasses, tap the touchpad once to pause or resume, or touch and hold to end the session. These two gestures belong to the glasses during a session, and the app never receives them. **Stop session** in the app ends it too.
4. If the card says *Capture button unavailable*, the reason is shown and spoken. The session and the in-app Solve button still work.

Caveats:
- **Inputs is experimental in SDK 1.0.** You can build and test with it, but apps that use it can't be published yet. Meta can also gate it per app or account: it has no permission prompt, and the glasses may refuse it (*permission denied*, *activation failed*, *unavailable*). It needs Meta AI app V290+ and glasses firmware V128+. The SDK reports Gen 1 and Gen 2 Ray-Ban Meta as the same model, so support is only known once you try.
- **How it stays running with the phone locked.** `bluetooth-central` keeps the connection, and a button press should wake the app. iOS gives a woken app roughly 30 seconds, which covers the photo. Claude can take longer, so while the answer is pending the app plays silent audio, which iOS allows for apps with the `audio` background mode. The spoken answer then keeps it running to the end. If time runs out mid-photo anyway, the app stops the camera cleanly, because a stream left running when iOS suspends the app can leave the glasses refusing sessions ([#231](https://github.com/facebook/meta-wearables-dat-ios/issues/231)).
- **Late presses are skipped.** If a press reaches the phone more than 5 seconds later than usual (for example, held back while iOS had the app suspended), the app says "That button press reached the phone late" instead of photographing a view that has probably changed. The diagnostics log shows the app state and delay for every press, so you can see whether presses wake the app with the phone locked.
- **Choose "Allow always" for camera access.** "Allow once" ends with the session, and Meta AI can't open to grant it again while the phone is locked.
- Presses less than 0.8 seconds apart count as one, and repeated presses while it's working get one "Still working" reply.
- Only a **short press** triggers a solve. Hold and double press are ignored.
- **How the button is wired (from Meta's BirdSpotter sample, which was tested on real glasses):**
  - The app asks for the temple touchpad and action button as well as the capture button. Asked for alone, the capture button once showed as active but sent nothing. Touchpad events are only logged. Single tap and tap-and-hold stay with the glasses, and volume stays with the system.
  - Taking a photo can drop button events, so the app re-adds them after every photo. It retries quietly a few times before reporting the button unavailable.
- **Locked phone:** the SDK pauses a raw video stream while the app is in the background, so photos taken then use the compressed (HEVC) stream, which keeps running.

**Troubleshooting**
- *Any error:* tap **Copy log** on the error alert, or open **Settings → Diagnostics log**. It records SDK setup, device state, each session and capture-button step, and the exact SDK error type and code. Paste it when reporting a problem.
- *Meta AI shows "Internal error — The operation could not be completed":* this message comes from the Meta AI app, not this app. Meta traced it to a Meta AI bug that lost the Developer Mode setting during approval ([SDK issue #205](https://github.com/facebook/meta-wearables-dat-ios/issues/205)). Fix: update Meta AI, force-quit and reopen it, and try again. If it persists, turn Developer Mode off and on in Meta AI (tap **Install** next to the glasses if it's shown). Then disconnect and reconnect the glasses from this app's Settings. Meta AI keeps only one Developer Mode app registered at a time, so registering another app (such as a Meta sample) unregisters this one.
- *Every session fails with "Session ended by device" or "Device unavailable":* turn the glasses off with the power switch and back on ([#292](https://github.com/facebook/meta-wearables-dat-ios/issues/292)). If Meta AI shows "broadcast in progress", stop it there. If needed, close the glasses in their case for about a minute ([#231](https://github.com/facebook/meta-wearables-dat-ios/issues/231)).
- *Versions:* SDK 1.0.0 needs Meta AI app V290+ and glasses firmware V128+. Older firmware can connect but still refuse sessions.
- *Meta SDK log:* **Settings → Diagnostics log → Share Meta SDK log** sends the SDK's own log files, which name link and authentication failures the app can't see.
- *No glasses found / timed out connecting:* unfold the glasses, check they're connected in Meta AI, and confirm Meta Developer Mode is still on.
- *Speech plays from the phone:* the glasses aren't the active Bluetooth audio output. Pick them in Control Center's audio route menu.
- *API key rejected:* re-enter it in Settings. Check the key's workspace has credit.

**Known SDK limits that affect this app (open issues on Meta's SDK repo)**
- **One camera stream per glasses session.** In SDK 1.0.0, starting the camera stream again after stopping it can fail at once with `StreamError.internalError` ("Critical error, the stream should end"); Meta says stop → photo → restart "isn't a pattern we'd recommend yet" ([#260](https://github.com/facebook/meta-wearables-dat-ios/issues/260)). Keeping one stream running isn't an option either, since a capture press during a running stream can pause the session instead ([#312](https://github.com/facebook/meta-wearables-dat-ios/issues/312)). So the app uses a fresh glasses session for every photo: right after each photo, while Claude works, it reconnects in the background (with Meta's 2-second gap) and re-attaches the button. If a photo still fails to start, it reconnects and retries once. The log shows "refreshing the glasses session".
- A capture-button press while a camera stream is running may pause the session instead of reaching the app ([#312](https://github.com/facebook/meta-wearables-dat-ios/issues/312)). This app runs the stream only for the second or two of each photo, so presses between photos shouldn't hit this.
- Starting a camera stream can stop Bluetooth audio playing through the glasses ([#256](https://github.com/facebook/meta-wearables-dat-ios/issues/256)). If the answer isn't heard in the glasses after a photo, that's the likely cause.
- The SDK leaks a little memory per second of streaming until the app restarts ([#324](https://github.com/facebook/meta-wearables-dat-ios/issues/324)). The short stream per photo keeps this small.

## Notes on the Claude call

- Model `claude-opus-5-5` with `output_config.effort: "medium"`. Setting `"low"` makes answers faster but less careful.
- The system prompt (`ClaudeClient.system`) writes for listening while looking at the paper, tuned for derivatives, limits and trig. It works as a **dictation machine**, by request: no explanations, rules or reasons, only what to put on paper. An answer is one sentence naming the problem (so a misread photo is caught at once), "You'll write N lines", the pen lines (Write / Continue / Mark), a box around the answer, and "Done." The math wording is based on:
  - **ClearSpeak**, the style screen readers use for students who listen to math, taken from the open-source [MathCAT](https://github.com/NSoiffer/MathCAT) rules: "sine squared of x", "the limit as x approaches 0 of", "the fraction with numerator … and denominator …, end fraction", "e raised to the exponent … end exponent".
  - **[Isaacson et al.](https://files.eric.ed.gov/fulltext/EJ1169645.pdf) (Purdue):** 75% of textbook expressions can be heard more than one way, mostly because nothing marks where a fraction, root or exponent ends, and inconsistent wording adds load. So the prompt marks starts and ends and uses one wording per notation.
  - **Mayer's multimedia principles:** name the structure up front, cut filler, talk to "you".
  - Pauses come from commas, not SSML, which is unreliable on iOS.
- **Dictation like a patient tutor.** The listener can't see anything and copies by ear, so answers say what the math *is*, never what it looks like, in plain classroom words: "u prime equals secant squared w", "x squared, plus 1", "w to the negative 8", "the limit as h approaches 0", "natural log of x", "negative 3" (a negative number) vs "minus" (taking away). Small fractions are "3 x over 2"; a big one is "a fraction", then "on top, you have …" and "on the bottom, you have …" on lines of their own. "End exponent", "end root" and "end fraction" are said only when more follows something long, so where it ends is never in doubt. There are no explanations: the answer only dictates. Answers use four kinds of pen line: **Write:** starts a new line on paper ("Start line 1"); **Continue:** stays on the same line ("Same line.", or nothing before a fraction's top or bottom); **Sentence:** is words to write out; **Mark:** is crossing out or drawing a box, said as one plain instruction ("On line 5, cross out both h's, the h on top and the h on the bottom"), followed by 2 seconds per thing to cross out. Each problem ends by boxing its answer line. The wording follows the rules human readers use to read math tests to students who can't see the page ([Michigan M-STEP read-aloud guidelines](https://www.michigan.gov/documents/mde/Math_and_ELA_Read-Aloud_Guidelines_512366_7.pdf)) and ClearSpeak, and was chosen by the user by ear.
- **A whole page at once.** Answers first say which problems are fully visible ("I can see problems 4, 5 and 6") and which to retake because they're cut off or blurry. Claude never guesses at a problem it can't fully read, and if none is complete it just asks for a retake. Each problem starts with a **Problem:** line: the app says "Problem 4.", pauses 2 seconds to find the spot on the paper, and starts the line count over at line 1. The answer ends with "Done." The wording builds on ClearSpeak and the [ETS test-reader guidelines](https://www.ets.org/disabilities/resources/test-reader-guidelines.html). The app reads Write lines a little slower than explanations, **a few words at a time, waiting after each part while you write it** (see *How the voice dictates* below). Turn off **Settings → Voice → Pause after each part of a line** to hear the whole line, then one pause. **Time to write each line** scales every writing pause.
- **Spoken as it arrives.** The answer is streamed from Claude and each line is spoken as soon as it's complete, so problem 1 starts while Claude is still writing the rest of the page (and a long page no longer hits the 180-second request limit, which now only applies to a silent connection). If the answer ends early, the app says so instead of sounding finished: "Stop. The answer ran out of room partway through problem 5, so its last line may be unfinished. Take a new photo of problem 5 and any after it." The same is said for a dropped connection or an answer stopped partway, and the notice is saved with the answer.
- **Natural pacing:** explanation text goes to iOS's speech engine as whole passages, so sentence pauses are the voice's own, and everything is queued at once with the engine's built-in pauses. (An earlier build spoke each sentence as a separate utterance with app-timed gaps, which sounded stop-start.)
- **Voices: Azure, Heart or Apple (Settings → Voice).** **Azure** (online, the clearest) uses Microsoft's neural voices (Ava, Andrew, Emma, Brian) through the [Speech REST API](https://learn.microsoft.com/en-us/azure/ai-services/speech-service/rest-text-to-speech) with your own key: create a Speech resource on the Free F0 tier at portal.azure.com (500,000 characters a month, about 600 answers), then paste its key and region in Settings. A whole pen line goes in one request, with its writing pauses inside it as SSML breaks, so it's one smooth, connected utterance; Heart, which made each short piece separately, sounded smeared and uneven. If Azure can't be reached, Heart takes over for two minutes, then Azure is tried again. Pen lines are spoken at 0.7 of the voice's own speed (about 100 words a minute) and other sentences at 0.85; the speed slider scales both.
- **Read-backs ("Check:" lines).** After a long or easy-to-get-wrong line, Claude reads it back in its own natural words ("Just to make sure you got all that, line 5 should look like ..."), varying the lead-in and skipping short lines, as a person dictating would. The app says it smoothly with a short beat and no writing time. Claude also puts the pauses where a person would (after each "equals", before each new term); the app sets each pause's length from how much there is to write.
- **Natural voice (built in):** answers are read by Kokoro's "Heart" voice (rated A, the best of Kokoro's voices; [voice ratings](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/VOICES.md)), run inside the app by [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx), so it works offline, with the phone locked, and doesn't depend on iOS sharing other apps' voices (iOS 26 doesn't reliably; Piper voices never appeared). Apple's Premium voices and Piper's LibriTTS voice were tried first and sounded robotic. The build downloads the voice files (about 160 MB, `kokoro-int8-multi-lang-v1_0`, Apache 2.0) into `Voices/kokoro`; they aren't in the repo. Each piece is made while the one before it plays and is followed by its writing pause as silence, so there are no stop-start gaps. **Settings → Voice** switches between Azure, Heart and an Apple voice; if no natural voice can run, Apple's voice is used automatically.
- **Voice:** **Settings → Voice** lists every installed voice with its quality (Default, Enhanced, Premium), with **Preview voice**. Default-quality voices sound robotic; download an Enhanced or Premium one in iOS Settings → Accessibility → Spoken Content → Voices → English, then pick it. "Automatic" uses the best one installed.
- **Conversations:** the speech-bubble button on the main screen. Each hands-free session is its own chat, which opens straight up while the session runs. When the session ends (Stop session, or touch-and-hold on the glasses) it's archived under **Past sessions**, and the next session starts a clean chat. Solve-button answers are grouped by day. Each chat shows the photo, prompt, answer (Write lines highlighted) or error, with **Play again**. Swipe a chat to delete it. Saved on the phone (last 300 answers); Test mode entries are marked.
- **Repeat a line:** double-tap the glasses' touchpad (it reaches the app as a "select" event without pausing the session, per Meta in [#312](https://github.com/facebook/meta-wearables-dat-ios/issues/312)), or tap **Repeat line** in the app. It says "Again." and dictates the latest Write line part by part, 10% slower, then continues where it left off. Ask again right away and it says "Again, slower." and goes slower still.
- Speech: **Settings → Voice** sets the speaking speed (default 0.42, aimed at about 150 words a minute) and has a **Test voice** button that plays a sample answer. As a safety net, notation that slips into an answer is read in the same forms ("sin²x" as "sine squared of x", "dy/dx" as "d y d x", "lim x→0" as "the limit as x approaches 0, of"); these rules are tested on sample answers.
- Server-side refusal fallback is on (`fallbacks: "default"`, beta header `server-side-fallback-2026-07-01`). If a safety classifier declines, Anthropic retries on its recommended fallback model instead of returning nothing. The app also handles `stop_reason: "refusal"`.
- Each Solve is one paid API request with one image. Typical cost is a few cents, depending on answer length.

## How the voice dictates

What the research says, and the setting each finding led to (`Speaker.swift`):

| Finding | Setting |
|---|---|
| Apple voices are tuned for their normal speed (0.5); slowing them stretches the sound and makes it flat and robotic, which the user heard as "very unhuman". Studies of synthetic speech favor slower speech for comprehension ((Higginbotham et al. 1994, *AAC* 10:191); Von Berg et al. 2009, *AAC* 25:7), but here the writing pauses already give the time. | Default speed **0.5**, the same for pen lines (they were 12% slower). An old saved speed starts over once at the new default. |
| Apple publishes no mapping from `AVSpeechUtterance.rate` to words per minute, and it differs by voice ([Apple forums](https://developer.apple.com/forums/thread/725313)). | The diagnostics log records **"measured N words per minute"** for each longer sentence, so speeds can be checked on the phone. |
| Working memory holds about **2 seconds of speech** (Baddeley, Thomson & Buchanan 1975), but a familiar phrase is held as one chunk, and dictation is given in meaningful chunks of a few words with a pause to write ([PLD](https://support.pld-literacy.org/en-au/article/how-do-i-implement-dictation-with-a-group-9r05k/)). Each new utterance also restarts the voice's intonation, so many tiny utterances sound stop-start. | Claude's commas are breaths, kept inside one utterance. The app **stops for writing only between whole pieces of math**: after "equals", or before a plus, minus or times that starts a new term outside parentheses. It never stops inside parentheses (unless they hold more than 14 marks, and then only between terms), between a coefficient and its variable, a function and its argument, something and its power, or before "close parenthesis" / "end exponent". Pieces are joined into parts of **up to 8 marks on paper** (at most 20 words), so "7 times, open parenthesis, 5 x squared, plus 2, close parenthesis" is one part and "minus 1, sine x" the next. Words that only say where to write ("on top, you have") lead into what follows. Sentence lines can stop at any comma. |
| Handwriting copy speed reaches about 24 wpm by grade 9, roughly 2 letters a second at full speed ((Graham, Berninger, Weintraub & Schafer 1998, *J. Educational Research* 92:42)). Writing math neatly is slower. | Writing pause = **0.7 s per character written** (at least 1.2 s per part), estimated from the spoken words: "cosine" = 3 (cos), "open paren" = 1, "squared" = 1, "fraction, top" = 0, numbers count their digits. Scaled by **Time to write each line**. |
| Pauses inside spoken math are what disambiguate structure, more than pitch ([Gellenbeck & Stefik 2009](https://digitalcommons.cwu.edu/compsci/22); Stevens & Edwards, MathTalk). | Structure comes from pauses between parts and from words that mark where things start and end ("open paren", "end fraction"). Pitch and volume stay at the voice's defaults. |
| iOS SSML adds extra pauses around tags ([Apple forums](https://developer.apple.com/forums/thread/712411)), and `ssmlRepresentation` froze apps in an iOS 18 beta. | No SSML. Each pause is the next utterance's `postUtteranceDelay`, queued with the speech. |
| Synthetic speech quality affects comprehension (Higginbotham et al. 1994). Neural voices sound more natural, but they can be slightly less intelligible in noise ([Cohn & Zellou 2020](https://par.nsf.gov/biblio/10275344)). | Use an **Enhanced or Premium** voice, not Default. In a noisy room, try both with Test voice. |
| Two established styles for speaking math: **MathSpeak** marks every start and end so an expression can be rebuilt exactly ([Isaacson, Schleppenbach & Lloyd 2014](https://repository.rit.edu/jsesd/vol14/iss1/3)); **ClearSpeak** reads like classroom speech and beat MathSpeak for understanding ([Frankel et al. 2016, ETS RR-16-23](https://www.ets.org/research/policy_research_reports/publications/report/2016/jwog.html)). Test readers for students with no visual reference read math the common way ("V equals four-thirds pi r cubed"), say "negative" for negative numbers, and show a fraction's grouping with a pause ("t minus 2 *(pause)* over t plus 8"). | ClearSpeak-style plain words, with MathSpeak's one essential idea kept only where needed: "end exponent", "end root" or "end fraction" when more follows something long. |
| People learn more when they first know the names and characteristics of the key parts (Mayer's pretraining principle, median d ≈ 0.85–0.92). Help that beginners need becomes redundant, and can even hurt, once they know it (expertise reversal, Kalyuga). | Each symbol's shape is described **the first time in an answer**, then only its name. The same words are used for a mark every time (Isaacson: inconsistent wording adds load). |
| Labeling each step's goal ("subgoal labels") helps novices learn procedures from worked examples (Margulieux & Catrambone, studies in programming, statistics and chemistry). Cues that show the structure help (signaling principle, median d ≈ 0.4–0.6). | Each step opens with a 2–4 word goal ("Factor the top."). Lines are announced "Start line N", and the answer is boxed. |
| Cancelling terms instead of factors is the most frequent error with algebraic fractions (Figueras et al. 2008; Mhakure et al. 2014). | Before a cross-out, the answer says *why* it cancels (it multiplies, so it divides out to 1) and, the first time, that a piece joined by a plus or minus sign can't be crossed out. Then a Mark line says exactly what to cross out and where. |
| Students who explain each step to themselves learn more from worked examples than those who only copy (Chi et al. 1989; Renkl). | Not added yet: an optional one-sentence prompt at the end, such as "Say to yourself why the x minus 2 cancelled." |

Example: *"Write: u prime equals secant squared w"* as line 2 is heard as
"Start line 2. u prime equals secant squared w." *(5.6 s + 1 s to move down a line)*. Writing time counts only the marks: "secant" is 3 characters (sec), "squared" is 1, "on top, you have" is 0 (so it leads straight into what goes on top), "over" and "on the bottom" are 1 (the fraction bar). A Mark line gets 2 seconds per thing to cross out or draw, up to 8.
- **What a calculus test needs (checked against a Math 131 derivatives practice exam).** Beyond the basics: a power on a power ("letter e, raised to the power of theta, with a tiny 2 raised on the theta"), subscripts for log bases ("the letters l o g, with a small b lowered below the line"), cube and fifth roots ("a root sign with a small 3 in its notch"), decimals ("4 point 9"), units as letters ("f t, raised to the power of 3, right beside that, slash, m i n"), lettered parts ("Problem 5, part A"), and **Sentence:** lines for answers that must be written out as words, which count every letter when timing the pause. Pictures are one **Mark:** line per shape.
- **The teacher's rules (from a graded worksheet).** Marks were lost for not rewriting a root or a fraction as powers before differentiating ("Rewrite h(w) first"), and for not showing the number put in for the variable before using values from a table. She accepts an exact answer ("you can stop here"), and a decimal was marked wrong. The quotient rule scored full marks when u, u prime, v and v prime were listed first. The prompt now has these rules, and the Test voice sample is that worksheet's quotient-rule problem written her way. A fraction inside a raised part is dictated with a slash ("w, raised to the power of minus 5, slash, 9"), as handwritten.
- **What the test covers (from the student).** The limit definition of the derivative will be on the test, along with the chain rule and all the log rules, so the prompt spells out how each must be answered: the limit definition step by step with the limit symbol kept until h is replaced and no shortcuts allowed (shortcuts earn no credit on those problems); the chain rule never stopping after the outside function; every log rule, expanded one rule per line before differentiating; and the derivatives of trig, exponential and log functions, including that a number like natural log of 7 differentiates to 0. It also covers evaluating a derivative at a point (a slope is f prime of the number, and the derivative of f of 3 is 0, which is not f prime of 3), implicit differentiation and related rates. Sources: common errors from [calculus misconception research](https://appspenang.uitm.edu.my/sigcs/2024-2/Articles/20244_ChainRuleErrorsInCompositeFunctionDifferentiation.pdf) (forgetting the inner derivative is the most common chain-rule error), [UBC's list of first-year calculus errors](https://personal.math.ubc.ca/~feldman/m100/warnings.pdf), and [Purdue's log-differentiation notes](https://www.math.purdue.edu/~msunkula/MA161/F25/Lesson17.html). **Settings → Voice → Test limit definition** plays the practice test's problem 4 worked from the definition (about 7 minutes).
